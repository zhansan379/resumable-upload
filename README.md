# 大文件分片上传 · 断点续传 / 秒传

Java (Spring Boot 3) + Vue 3 实现的大文件上传方案。文件切成小片并发传、断了能续、重复文件直接秒传、刷新页面任务还在、传完还会校验完整性。零数据库依赖，开箱即跑。

方案设计基于对 GitHub 高 star 开源项目的调研（uppy、blueimp、filepond、fine-uploader、plupload、resumable.js、flow.js、simple-uploader、tus、free-fs 等 10 多个项目）。

## 功能清单

- **分片上传**：文件在浏览器里切成小片（默认 5MB 一片），多片同时传（默认 3 片并发，可调到 1~6），弱网下比整文件单发更稳。
- **断点续传**：传之前先问服务器“这个文件哪些片已经有了”，已传的直接跳过。进度以服务器磁盘为准，服务端重启、浏览器刷新都不丢。
- **刷新恢复**：任务记录在浏览器本地持久化，刷新或重开页面后任务自动回来——正在传的任务接着传，主动暂停的任务恢复成待继续。还能记住算好的 MD5，不用重算。
- **秒传**：浏览器在后台线程算出整个文件的 MD5 发给服务器，服务器一查索引发现已经有相同内容，直接返回，一个字节都不用传。
- **暂停 / 恢复**：点暂停就中断正在传的分片；点继续时重新和服务器对齐进度，接着传缺的片。
- **失败自动重试**：网络抖动或服务器 5xx 时，分片自动按 1 秒、2 秒、3 秒退避重试 3 次；如果是 4xx 这类参数错误就直接报错，不重试浪费。
- **显式合并**：全部片传完，前端主动发一次“合并”请求，服务器按分片号顺序拼成完整文件，加锁防止同一文件被并发合并，合并前先检查分片齐不齐、总大小对不对。
- **完整性校验**：合并完成后服务器在后台重新算一遍整体 MD5 和前端给的值比对，结果在文件列表里显示“通过 / 校验中”。很多开源实现都缺这一步。
- **下载**：文件直读直发不占内存。支持 HTTP Range 断点下载，浏览器和 IDM 这类下载工具可以接着下、多线程加速。
- **文件管理**：文件列表、下载、删除；点取消上传会把服务器上的分片临时目录一并清理。

## 效果展示：测试与验证

用 JMeter 5.6.3 跑同一套测试计划（7 组场景、176 个请求），分别在**本机回环**和**公网服务器（阿里云）**各跑一遍，**两次都 0 错误**。报告生成方法见 [jmeter/README.md](jmeter/README.md)。

### 覆盖度：功能全链路 + 异常路径都有兜底

| 用例组 | 场景 | 结果 |
|--------|------|------|
| 02-完整上传 | 清理残留 → check → 20 片上传 → 合并 → 秒传复核 | ✅ 通过 |
| 03-秒传 | 同 hash 再 check | ✅ 命中，57ms |
| 04-下载 | 整文件 200 / Range 区间 206 / 超界 416 / 条件不匹配回退 200 | ✅ 4 条全过 |
| 05-断点续传 | 传一半 → 合并 409 → 断点探测 → 补齐 → 重复合并幂等 | ✅ 通过 |
| 06-异常边界 | 非法 hash 400 / 分片越界 400 / 缺参数 400 / 只传 1/3 片 409 | ✅ 全过 |
| 07-并发负载 | 5 线程 × 20 片 × 5MB 并发上传后删除 | ✅ 0 错误 |

> 每组运行前自动清理上次测试残留（01 组），保证结果可重复。本地与公网各跑一遍全部通过——这是“服务可用”的完整证据链。

### 性能：公网（阿里云，服务器带宽 100Mbps）

- **分片上传 140 次平均 4198ms**：瓶颈是客户端上行带宽（约 25Mbps），5 线程并发共享管道后单片延迟升到 3~7 秒。
- **下载 100MB 17.8 秒（约 5.6MB/s）**：服务器带宽 100Mbps，实测下载约 45Mbps——受限于客户端到服务器的公网链路，未达到服务器带宽上限。
- **秒传 57ms、合并约 488ms**：跨公网的元数据接口依然毫秒级。

![公网统计总表](docs/images/jmeter-remote-statistics.png)

![公网响应时间曲线](docs/images/jmeter-remote-over-time.png)

- **曲线解读**：分片上传主曲线在负载组 5 线程启动后从 1~2 秒抬升到 3~7 秒并抖动，结束后瞬间回落——这是 5 条连接瓜分同一条上行管道的带宽争用，不是服务端瓶颈；浅蓝那个点是 100MB 下载 17.8 秒，单独执行不与上传争抢。

### 性能：本地（NVMe SSD，网卡 300Mbps）

- **分片上传平均 101ms、P95 128ms**：5MB 一片稳定在 0.1 秒，并发期间几乎不变。
- **下载 100MB 655ms（约 192MB/s）**：本地回环不受网卡 300Mbps 限制，直读直发跑满磁盘管道。
- **合并 100MB 约 270ms**：并发合并时升到 370~390ms，仍远低于 1 秒。

![本地统计总表](docs/images/jmeter-local-statistics.png)

![本地响应时间曲线](docs/images/jmeter-local-over-time.png)

- **本地数据的意义**：本地没有带宽瓶颈，分片延迟稳定在 0.1 秒——证明**服务端代码路径本身不是瓶颈**，公网慢是带宽的问题。本地测试的真正价值是在最快路径上暴露逻辑问题（比如 deleteFile 误删目录的 bug 就是本地下载用例 404 暴露的）。

现有测试证明了核心路径的正确性和默认参数下的可用性，以下用例能进一步证明服务的健壮性与相对优势：

- [ ] **参数扫描**：2MB / 10MB / 20MB 分片 × 并发 1 / 3 / 6，验证默认参数（5MB / 并发 3）是否是最优工作点，以及大分片高并发时合并与 IO 是否稳定。
- [ ] **边界文件**：0 字节文件、刚好 1 个分片大小的文件、刚好达到大小上限的文件、1000 个 1MB 小文件并发上传，验证边界条件与合并风暴下的行为。
- [ ] **对抗性中断**：合并进行到一半强杀服务端（验证索引与文件不一致的恢复）、上传中磁盘满、上传中后端 OOM，验证异常路径的兜底能力。
- [ ] **弱网注入**：用 toxiproxy 注入丢包 1% / 5%、延迟 100ms、带宽限制，验证丢包环境下重试与断点恢复的成功率，以及乱序 / 重复包下分片写入的幂等性。
- [ ] **基线对比**：同一文件分别走“整文件单请求上传”和“分片上传”，对比弱网下的重传字节量与总耗时，量化分片设计的收益。
- [ ] **横向对比**：与 free-fs / tusd 等主流开源方案在相同环境、相同负载下压测，对比吞吐、恢复成功率与资源占用，明确相对位置。
