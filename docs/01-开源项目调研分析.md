## 二、逐项目实现分析

### 2.1 transloadit/uppy（~31k★）

- **架构**：`@uppy/core` + 插件。续传由 `@uppy/tus`（封装 tus-js-client）承担；另有 `@uppy/golden-retriever` 将文件与上传状态存入 IndexedDB，浏览器崩溃/刷新后可恢复。
- **分片**：默认 `chunkSize: Infinity`（整文件单请求，续传靠 offset 而非分片）；可配置后按 `Blob.slice` 切 PATCH 包体，配 `parallelUploads` 需服务端支持 tus **concatenation** 扩展。
- **文件指纹**：元数据指纹 `'tus-br'-name-type-size-lastModified-endpoint`，**不是内容 hash**，只能“恢复上次传输”，不能秒传。
- **续传**：`POST /files` 创建（`Upload-Length`/`Upload-Metadata`）→ `PATCH`（`Upload-Offset` 头）追加 → 断线后 `HEAD` 读服务端 `Upload-Offset` 续传；上传 URL 持久化在 localStorage。
- **暂停/重试**：`abort()`（默认保留服务端资源）/`start()`；`retryDelays: [0,1000,3000,5000]`，429/409/423/5xx 指数退避，监听 `online` 断网自动恢复。
- **并发**：`limit: 20`，共享 `RateLimitedQueue`，429 全队列退避。
- **秒传**：不支持。

### 2.2 blueimp/jQuery-File-Upload（~30.7k★）

- **分片**：默认不分片（`maxChunkSize: undefined`）；开启后 `slice(file, uploadedBytes, uploadedBytes+maxChunkSize)` 逐片递归上传。
- **标识**：**无 uuid**，每片就是普通 multipart POST（字段 `files[]`），位置信息靠请求头 `Content-Range: bytes start-end/total`。
- **续传**：**Range 头双向协议**——客户端带 `Content-Range`，服务端响应 `Range: bytes 0-n/total`，客户端解析出“服务端已收字节数”作为下一片起点。**服务端权威**，天然容忍重复/乱序片。
- **合并**：服务端按 Range 自行追加，各语言 server 示例自行实现。
- **重试/并发**：核心库无内置重试（需在 `chunkfail` 回调自实现）；`limitConcurrentUploads` 可配。
- **借鉴**：`Content-Range` 协议零侵入、服务端权威偏移的思想；短板（无标识、无重试）正是自研必须补齐的部分。

### 2.3 pqina/filepond（~15k★）

- **分片**：`chunkUploads: true` + `chunkSize` 默认 **5MB**，`file.slice(..., 'application/offset+octet-stream')` 循环切块；`chunkForce` 可强制小文件分片。
- **续传三步流**：① `POST`（空体，`Upload-Length` 头）→ 文本响应返回 transfer id；② 逐片 `PATCH ?patch=<id>`（`Upload-Offset` 头）；③ 恢复时先 **`HEAD`** 读 `Upload-Offset`，小于该偏移的分片直接标记 COMPLETE。
- **标识**：transfer id 由服务端首次 POST 返回，即最终文件 id，无内容 hash。
- **合并**：无显式合并请求，服务端按 offset 顺序 append，传完 transfer id 直接生效。
- **暂停/重试**：每片独立 `retries: [500,1000,3000]` 数组依次延迟重试；文件级 `maxParallelUploads: 2`，分片级串行（单飞行）。
- **特色端点**：`revert`（DELETE 临时文件）、`restore`（按 id 恢复会话）、`load`/`fetch`。

### 2.4 23/resumable.js（~4.7k★）—— “分片表”流派鼻祖

- **分片**：默认 1MB，`forceChunkSize=false` 时末片不裁剪（**末片最大约 2×chunkSize**），Java 端必须按 `currentChunkSize` 实际字节写盘。
- **标识**：默认 `size + '-' + 去特殊字符的文件名`，可覆盖 `generateUniqueIdentifier`（支持异步，社区常改为整文件 MD5）。
- **续传**：`testChunks: true`，每片上传前先 **GET 探测**（参数与 POST 完全相同），**200 = 该片已存在直接跳过**，建议“不存在”返回 204。
- **合并**：无内置端点；收到第 `totalChunks` 号片即可由服务端重组，须容忍同片重复上传。
- **重试/并发**：`maxChunkRetries`（README 写无限，源码默认 100）、`permanentErrors=[400,401,403,404,409,415,500,501]` 命中即放弃；`simultaneousUploads: 3`。
- **秒传**：无（无 hash 能力）。

### 2.5 flowjs/flow.js（~3.0k★）与 simple-uploader/Uploader（~0.9k★）

flow.js 是 resumable.js 的重构分支（参数前缀 `flow*`，类拆分为 Flow/FlowFile/FlowChunk，配置支持“值或函数”）。

simple-uploader.js（vue-simple-uploader 底层）在 flow.js 基础上又重构（uploader/file/chunk 三类 + 异步事件），关键增强：

- **`checkChunkUploadedByResponse(chunk, response)`**：不做逐片 GET，而是在**第一个分片成功响应后**解析响应体得到“哪些片已存在”，一次请求恢复全部进度——三库中最高效的续传探测。
- **秒传标准姿势**（社区实践）：`fileAdded` 钩子中用 **spark-md5 + Web Worker 分片增量计算整文件 MD5** → 请求服务端 check → 命中即秒传；否则把 MD5 设为 identifier，配合 `checkChunkUploadedByResponse` 实现“秒级续传”。
- `fileSuccess` 仅在**全部分片完成**时触发一次 → 在此回调调用合并接口是标准做法。
- 默认 1MB/片、并发 3、`maxChunkRetries=0`、成功码 200/201/202。

### 2.6 tus 协议 / tusd（~3.9k★）与 tomdesair/tus-java-server

- **协议核心**：`POST` 创建（`Upload-Length` + `Upload-Metadata`）→ `HEAD` 查 `Upload-Offset` → `PATCH`（`application/offset+octet-stream`）追加写，偏移不匹配返回 `409 Conflict`；`checksum` 扩展用 `Upload-Checksum` 校验块（不匹配 460 丢弃重传）。
- **扩展**：`creation-with-upload`（创建即传，小文件一步完成）、`concatenation`（并行分片拼接）、`termination`（DELETE 清理）、`expiration`（过期 410）。
- **tusd 存储**：filestore 布局为 `[id]` 数据文件 + `[id].info` JSON 元数据（Offset、MetaData、IsPartial…），数据用 `O_APPEND` 追加，**元数据与数据分离**；上传资源加锁，冲突返回 `423 Locked`。
- **Java 集成**（tomdesair/tus-java-server）：`TusFileUploadService` 单例 Bean，`process(request, response, ownerKey)` 统一处理 POST/PATCH/HEAD/DELETE，带基于校验和的**上传去重（秒传）**、完成回调监听器、租约锁与定时 `cleanup()`。
- **状态码语义**：409 偏移冲突（客户端重新 HEAD）、412 版本不匹配、423 资源被锁、460 校验失败、413/415/404/410 各司其职——前端据此精确区分“重试 / 重传分片 / 重建上传”。

### 2.7 FineUploader/fine-uploader（~8.1k★）

- **分片**：默认关，`partSize` 2MB，`concurrent.enabled` 控制分片是否并发。
- **标识**：客户端生成 **UUID（qquuid）贯穿全生命周期**（三库中最优标识设计）；分片参数 `qqpartindex/qqpartbyteoffset/qqtotalparts/qqtotalfilesize/qqfilename`。
- **续传**：`resume.enabled` 默认关；5.x 为 **localStorage 方案**——按 `name+size+chunkSize+endpoint` 生成持久化 key，记录 uuid + 剩余分片索引，7 天过期，刷新页面不丢进度。
- **合并**：默认服务端收最后一片自行合并；配 `chunking.success.endpoint` 后发**显式合并 POST**（`qquuid/qqfilename/qqtotalparts`）——并发分片时必须配置，语义清晰。
- **特色**：响应 `reset:true` 可强制客户端重传整个文件；`retry.maxAutoAttempts=3` + 5 秒退避。

### 2.8 moxiecode/plupload（~5.6k★）

- 多 runtime（HTML5/Flash/Silverlight）均可分片，`chunk_size` 默认 0（禁用）；HTML4 iframe 无法分片。
- **标识最弱**：仅靠 `name + chunk + chunks` 三参数关联，同名文件并发上传互相污染；**无内置续传**（官方 Wiki 建议服务端自建分片状态探测）；合并靠 PHP 示例“首片 wb 建 .part、后续 ab 追加、末片 rename”，强依赖顺序到达。
- **反面教材价值**：文件名做关联键、纯 append 合并、无探测——正是自研要规避的设计。

### 2.9 Java 全栈落地参考（dromara/free-fs 等）

| 仓库 | 模式 | 分片记录 | 秒传 | 合并 | 校验 |
|------|------|----------|------|------|------|
| dromara/free-fs | 后端中转 → S3 multipart | Redis（chunkIndex→eTag）+ DB 任务表 + `GET /transfer/chunks/{taskId}` 返回已传分片集合 | ✅ `(md5,size)` 引用计数复用 | `completeMultipartUpload` + **Redis 分布式锁 + 状态机** | 仅 eTag 非空，无整体 MD5 |
| KKJava1/Upload-Springboot-Minio-liveplayer | **预签名 URL 直传 MinIO**（后端零带宽） | DB + `listParts` 以存储端为事实源 | 仅对象存在判断，无跨用户复用 | 存储端合并 | 仅比对分片数 |
| hsw409328/spring-boot-chunk-upload | 后端流式转发 OSS | Redis（eTag JSON，5h TTL） | ❌ | OSS 端 | ❌；eTag 读-改-写非原子 |
| yuxiao97/SpringBootChunkUploader | 本地 `RandomAccessFile.seek(offset)` 直写最终文件（**免合并**） | `.conf` 进度位图文件 | ❌ | 无需合并 | ❌ |

共性结论：MD5 均由**前端 spark-md5 分片增量计算**（后端不重算大文件 hash）；普遍缺失合并后完整性校验、孤儿分片清理、分片幂等；free-fs 的“任务状态机 + 分布式锁 + 引用计数秒传”最接近生产水准。

**两大协议流派**：

- **分片表模式**（resumable 谱系 / fine-uploader / free-fs）：文件切成 N 片，服务端记录“已传分片集合”，客户端跳过已传片，最后显式合并。适合并行分片、秒传、分片校验；需要维护分片状态与合并事务。
- **offset 流模式**（tus / filepond / blueimp-Range）：服务端维护“已收字节偏移”，数据只能追加写，HEAD 查询恢复。免合并、状态机简单、天然防乱序；但并行需 concatenation 扩展，难以做分片级校验与去重。

## 四、关键设计结论（自研方案的依据）

1. **文件标识必须用内容 hash**：resumable.js 默认 `size+文件名` 会把“同名同大小不同内容”误判成同一文件；plupload 纯文件名更不可取。自研应在前端用 spark-md5（Web Worker，2MB 分片增量）计算整文件 MD5 作为 identifier —— 同时是秒传和断点续传的 key（simple-uploader 社区方案 + free-fs 验证）。
2. **续传探测用“一次返回已传分片列表”**（simple-uploader `checkChunkUploadedByResponse` 模式）：一个 `/check` 接口同时解决“秒传”与“断点恢复”，避免 N 次逐片 GET（resumable.js）或复杂 HEAD 状态（tus）。
3. **显式合并端点**（fine-uploader `success.endpoint`）：全片完成后由前端发起合并请求，语义清晰、便于加锁防并发合并；服务端**按片号顺序 append**，兼容乱序到达（tusd filestore 的追加写 + RandomAccessFile 偏移直写两种实现均可，本方案采用顺序 `FileChannel` 合并）。
4. **补齐开源项目普遍缺失的三件事**：
   - **合并后完整性校验**：先校验分片数量与总字节，合并完成后后台重算 MD5 比对（异步，不阻塞响应）；
   - **分片写入原子性**：临时文件 + `ATOMIC_MOVE`，防止“半个分片”被当作已传；
   - **孤儿分片清理**：合并成功即删除分片目录，提供取消清理端点（filepond `revert` 思想）。
5. **状态码语义**（tus）：400 参数错误 / 409 分片缺失或重复合并 / 413 超限 / 415 类型错误；前端把 4xx 永久错误与可重试错误（网络/5xx）分类处理。
6. **暂停/恢复**：AbortController 中断在途分片（uppy/filepond），已传分片状态以**服务端磁盘为事实源**（free-fs 查询接口思想），前端刷新页面后重算 MD5 + 重新 check 即可恢复，可再用 localStorage 缓存 hash 减少重复计算（fine-uploader resume 方案）。
7. **并发控制**：文件级并发 1、分片级并发 3（各库默认值 2~3 的共识），失败指数退避重试 3 次。

## 五、本项目实现方案（吸收点映射）

| 借鉴来源 | 吸收点 | 本项目落地 |
|----------|--------|-----------|
| simple-uploader + free-fs | 一次 check 返回已传分片列表 | `POST /api/upload/check`（finished=秒传 / uploadedChunks=断点恢复） |
| simple-uploader 社区方案 | spark-md5 + Worker 整文件 MD5 | 前端 `md5Worker.js`，2MB 分片增量计算，带进度 |
| resumable.js | 分片参数协议 | fileHash/chunkIndex/totalChunks/chunkSize/totalSize/fileName |
| fine-uploader | 显式合并端点 + UUID 语义（以 MD5 代替） | `POST /api/upload/merge`，`synchronized(fileHash)` 防并发合并 |
| tusd filestore | 磁盘为事实源 + 元数据分离 | 分片目录 `data/upload/chunks/{fileHash}/`、hash 索引 `index.json`（重启不丢） |
| tus | 状态码语义 + checksum | 400/409/413/415 分类；合并后异步重算 MD5 校验 |
| blueimp | 服务端权威进度 | check 以服务端磁盘分片为准，前端缓存仅加速 |
| filepond | revert 清理端点 | 合并成功删分片目录；`DELETE /api/files/{hash}` 删除 |
| free-fs | 任务状态、锁、引用计数（简化版） | hash 索引去重即秒传；合并锁；文件列表/下载 |
| KKJava1 | （可选扩展）对象存储预签名直传 | 预留 StorageService 接口，本地磁盘为默认实现 |

技术栈：**Spring Boot 3.5 (Java 17) + Vue 3 + Vite + Element Plus + axios + spark-md5**，零数据库依赖（磁盘 + index.json 持久化），开箱即跑。
